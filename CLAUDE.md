# CLAUDE.md — `reboot-patterns`

> AI-assistant conventions for this repository. Every skill (`/teach-me`, `/PD`, `/grill-me`, `/spec`, `/to-issues`, `/pick-issue`, `/generate-tests`, `/reflect`, `/doc`) reads this file on every invocation. Anything not stated here, the AI will get wrong.

## 1. Project purpose

This repo teaches 8 distributed microservices patterns by building one Gradle subproject per pattern in an e-commerce domain (`order`, `payment`, `inventory`, `shipping`, `notification`). Services are deployed as K8s Deployments in the `reboot-patterns` namespace and connect to shared infra (MariaDB, Kafka, Redis, WireMock) via NodePort. Each pattern is "done" only when its canonical-failure bash test passes.

The full curriculum, lifecycle, and rationale live in the main PD (Notion). This file is the operational rulebook for code generation and tooling.

## 4. Per-subproject template

Every `patterns/p<N>-<pattern>/` subproject MUST follow this shape:

~~~
patterns/p<N>-<pattern>/
├── README.md                      # ~20 lines, generated by /doc — see §10
├── build.gradle                   # ~30–50 lines, references libs.* from catalog
├── Dockerfile                     # minimal single-stage eclipse-temurin:21-jre image
├── k8s/                           # K8s Deployment + Service manifests for this pattern's services
├── src/main/java/com/reboot/patterns/p<N>/<pattern>/
│   ├── <Pattern>Application.java
│   ├── api/                       # controllers (sync) / consumers (async)
│   ├── domain/                    # entities, value objects
│   ├── service/                   # business logic
│   ├── infra/                     # JPA repos, Kafka producers, Redis clients
│   └── config/                    # Spring @Configuration
├── src/main/resources/
│   ├── application.properties
│   └── db/migration/              # Flyway: V001__init.sql, V002__...
└── src/test/java/...              # MINIMAL JUnit only (see §7)
~~~

`application.properties` MUST connect to NodePort hosts (default `localhost:<nodeport>`), use the schema/topic/key prefixes from §5, and externalise nothing else. No profiles, no Spring Cloud Config in v1.

## 5. Naming conventions (mandatory)

| Concern | Pattern | Example (for pattern 3, outbox) |
|---|---|---|
| Java package root | `com.reboot.patterns.p<N>.<pattern>` | `com.reboot.patterns.p3.outbox` |
| Gradle module path | `:patterns:p<N>-<pattern>` | `:patterns:p3-outbox` |
| DB schema | `p<N>_<pattern>` | `p3_outbox` |
| Kafka topic | `p<N>.<pattern>.<event>` | `p3.outbox.order-confirmed` |
| Consumer group | `p<N>.<pattern>.<service>` | `p3.outbox.notification` |
| Redis key prefix | `p<N>:<pattern>:` | `p3:outbox:idem:` |
| K8s namespace | always `reboot-patterns` (shared) | — |

If you generate code that violates these prefixes, the cross-pattern logical isolation breaks. Treat these as compile errors.

## 6. Commit conventions

Format: `pattern(p<N>-<pattern>): <imperative summary>`

Examples:
- `pattern(p3-outbox): add poller publisher`
- `pattern(p3-outbox): make outbox row insert transactional with order insert`
- `pattern(p4-saga-choreography): handle PaymentFailed by emitting compensating InventoryRelease`

Rules:
- One logical change per commit. Mixing concerns breaks `/generate-tests` and `/reflect`.
- The pattern slug in parentheses is **required** so `/generate-tests` knows which pattern's `tests/` folder to write to.
- Pure refactors: prefix summary with `refactor:` (e.g. `pattern(p3-outbox): refactor: extract OutboxRepository`). `/generate-tests` will skip these.
- No "WIP" commits in main history.

## 7. Testing rules

Two test surfaces, with hard caps:

**JUnit (pure-logic only):**
- Allowed: MapStruct mappers, validators, simple stateless domain rules.
- Forbidden: `@SpringBootTest`, `@DataJpaTest`, MockMvc full-stack, Mockito-heavy layered tests, **Testcontainers**.
- Cap: ~5 unit tests per subproject. Justify additions.
- Authored inline by `/pick-issue` during implementation. Never authored by `/generate-tests`.

**Bash (pattern proof — primary):**
- One file per scenario under `tests/p<N>-<pattern>/<scenario>.sh`.
- Every script MUST start with `source ./tests/p<N>-<pattern>/reset.sh`.
- Every script narrates each step: `echo "Step N: <action>"` before the action.
- Every script asserts loudly on failure and `exit 1`.
- Failure injection uses §8 idioms only.
- The **canonical-failure scenario** for the pattern is the definition-of-done gate.
- Authored only by `/generate-tests`, from a single commit's diff + message.

`reset.sh` per pattern:
- Truncates that pattern's MariaDB schema (drop+recreate).
- Deletes that pattern's Kafka topics (prefix `p<N>.<pattern>.`).
- Resets that pattern's WireMock stub mappings (DELETE `/__admin/mappings` filtered by metadata).
- Idempotent. Safe to run anytime.

## 8. Failure-injection idioms (the only approved recipes)

`/generate-tests` and any hand-written test script MUST use these exact idioms:

| Failure | Recipe |
|---|---|
| Service down | `kubectl scale deployment/<svc> --replicas=0 -n reboot-patterns` (then back to 1) |
| Service slow | WireMock `fixedDelayMilliseconds` stub, or Resilience4j-side timeout for own behaviour |
| Kill broker | `kubectl delete pod -l app=kafka -n reboot-patterns` (StatefulSet recreates) |
| Crash app mid-flight | Run app under `bootRun`; the script `kill -9 $PID` after a marker log line is tailed |
| Network partition | `kubectl exec <pod> -n reboot-patterns -- iptables -A OUTPUT -p tcp --dport <port> -j DROP` (and `-D` to undo) |
| Duplicate event | `kafka-console-producer.sh` with the same payload twice |
| Poison event | `kafka-console-producer.sh` with a malformed JSON payload |

Do not invent new injection methods.

## 9. External APIs

All external HTTP calls MUST go through WireMock at `http://<node>:30080`.

- Pattern-specific stubs are POSTed by the test script at setup, deleted at teardown. Stub `metadata.pattern: p<N>` is required so `reset.sh` can target them.
- Cross-cutting reusable stubs (mock payment gateway, mock email gateway) live permanently in `mocks/stubs/` and are loaded at WireMock boot.
- No live external HTTP calls in any runtime path or test path. If a real endpoint is needed, refuse and ask.

## 11. Out of scope (HARD RULES — refuse)

If the user (or another skill) asks for any of these, refuse and link to the main PD's "Out of scope" section.

- Testcontainers in any form.
- Eureka, Consul, ZooKeeper-based discovery, or any non-Kubernetes registry.
- Event Sourcing.
- Confluent Schema Registry, Avro, Protobuf payloads.
- Service Mesh (Istio, Linkerd, Cilium service mesh).
- Kubernetes Operators.
- Two-Phase Commit / XA transactions.
- Splitting `reboot-patterns` into multiple repos.
- Hexagonal / Clean architecture / ports-and-adapters layering in pattern 1. Wait until a second pattern justifies the abstraction.
- Helm, Skaffold, Kustomize abstractions, Tilt, Telepresence, or any infra tool other than `kubectl`.
- Spring Cloud Config Server, Spring Cloud Bus.
- Multi-stage or complex Dockerfiles. Each service gets exactly one minimal single-stage `eclipse-temurin:21-jre` Dockerfile. No build tooling inside the image.

These rules are non-negotiable. If you believe one is wrong, raise it; do not bypass.

## 12. Beginner mode

The user is intentionally a beginner on these patterns. Optimise generated code for **comprehension**, not elegance:

- Prefer **explicit over clever**: explicit `@Bean` definitions over auto-config magic; explicit JPA entity fields over Lombok-`@Data`-everywhere.
- Add a 1–3 line **"why this exists" comment** at the top of every class introduced for pattern reasons (e.g. on the `OutboxPoller`, on the `SagaOrchestrator`).
- Do not introduce abstractions, base classes, generic types, or design patterns until a *second* pattern subproject demonstrably needs them. Duplication beats premature DRY.
- When two valid implementations exist, pick the one with fewer files.
- Never emit a TODO without a corresponding GitHub issue link.
- If a Spring Boot starter could replace 30 lines of code, prefer the starter — but document which auto-configurations it activates.

When in doubt: **simpler, with a comment explaining why**.
